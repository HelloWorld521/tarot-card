# 01 · 决策记录

按发生顺序排列。每条都写清「当时为什么这么选、为此放弃了什么」，因为三个月后真正需要回忆的是第二栏，不是功能本身。

---

## 1. 做「角色卡系统」，不是一次性性格测试

| 栏 | 内容 |
|---|---|
| 背景 | 最早的形态很容易滑向「答几道题 → 出一个结果页 → 截图走人」。这样每次打开都是从零开始，玩家没有理由回来第二次，结果也没有重量。 |
| 决定 | 把产物做成一张可保存的「角色卡」：有名字、有头像（名字哈希出颜色 + 首字）、有关系、有三个品质和三条代价，并且进入通讯录。通讯录是 `state.contacts` 对象数组，持久化在 `localStorage` 的 `tarot-lover-cards-v1` 键里，支持翻牌、查看详情、删除单张。 |
| 放弃了什么 | 放弃了一次性结果页的轻量：现在必须处理持久化、旧数据结构兼容、删除确认、空状态。也放弃了「随机生成一个陌生人」的玩法，所有卡都必须由玩家亲手选出来。 |
| 日期 | 2026-11-07 |

## 2. 先选后翻，建卡前不允许看到代价

| 栏 | 内容 |
|---|---|
| 背景 | 如果选卡时就能看到代价，玩家会把它当成一道算术题：比较哪个品质「性价比」最高。整个体验会从「凭直觉挑人」退化成「做最优解」。 |
| 决定 | 选卡网格 `buildTraitGrid` 只渲染品质名与正面场景（`name` / `frontScene`），完全不读 `costLabel` 与 `backScene`。进入翻面页后，`buildReveal` 才把背面内容写进 DOM，`startRevealSequence` 依次翻开三张。 |
| 放弃了什么 | 放弃了「透明选卡」带来的掌控感，也放弃了让玩家在选卡阶段就看到风险提示的可能性。代价是翻面必须做成一场有节奏的仪式（逐张、有间隔），否则玩家会觉得被戏弄。 |
| 日期 | 2026-11-07 |

---

## 3. 互斥特性不禁用，而是生成「矛盾体」

| 栏 | 内容 |
|---|---|
| 背景 | 「专一」和「自由」在语义上互斥，「大方」和「踏实」也互相拉扯。最直觉的做法是选中一个就把另一个灰掉，但这会让玩家一眼看穿规则，也砍掉了最有戏剧性的组合。 |
| 决定 | 不禁用任何卡。互斥组合照常可选、照常出结果，只是 `data/combos.js` 里给这类组合标记 `paradox: true`；结果页与分享图右上角显示「矛盾体」小标记。现有两组：专一 + 自由、大方 + 踏实。 |
| 放弃了什么 | 放弃了规则上的「自洽」和可解释性：玩家可能选中一对互相打架的品质，而系统不会阻止。换来的是更强的表达力和更值得分享的结果。代价是文案必须能同时承接两种品质，不能让玩家觉得系统算错了。 |
| 日期 | 2026-11-07 |

---

## 4. 特性文案采用「同一场景两种走法」

| 栏 | 内容 |
|---|---|
| 背景 | 写「优点」很容易，写「代价」很容易变成另一张卡。比如「温柔」配「没主见」，如果两边各写各的场景，读者感受不到它们是同一个人身上的同一件事。 |
| 决定 | 每张卡的 `frontScene` 与 `backScene` 写同一个具体场景的两种走向。例如「温柔」正面是崩溃时什么都不说只抱住你，背面是问吃什么永远「都行」；「浪漫」正面是凌晨三点去海边，背面是凌晨三点说分手、五点又说对不起。 |
| 放弃了什么 | 放弃了用形容词概括性格（「他很温柔」这种写法），也放弃了给每张卡写更多独立故事。代价是每张卡只能承载一个场景，扩写时必须守住「同一场景」这条线，否则卡片之间的对照关系会散掉。 |
| 日期 | 2026-11-07 |

## 5. 卡池 + 四维权重，用来调平衡（2026-11-07 修订为 16 张）

| 栏 | 内容 |
|---|---|
| 背景 | 卡池如果只靠文案，会很快被玩家摸清「哪三张最划算」；而纯随机生成又会让结果不可解释、分享出去也对不上。 |
| 决定 | 固定 16 张卡（原 12 张 + 第 9 条新增 4 张），每张带四维权重 `axes`：`security`（安全感）、`space`（空间）、`stability`（稳定）、`intensity`（强度），取值 -3～3。`computeResult` 把所选三张的四个维度分别求和，取最低的一维，用 `config.weakSentence` 的 `{weak}` 模板生成一句弱点台词；同时按第 11、12 条公式算出总分与四维分项。组合匹配先筛出所有命中的对子，再随机取一条（见第 13 条）。 |
| 放弃了什么 | 放弃了随机文案与动态难度，也放弃了「每张卡强度拉平」的设计。不同维度天然有高有低，某些组合就是会更「惨」，这是有意的。代价是新增卡时必须同时给出四维权重，并接受它可能改变现有组合的弱维结果与总分。 |
| 日期 | 2026-11-07 |

## 6. 分享图只露正面，不放任何代价

| 栏 | 内容 |
|---|---|
| 背景 | 分享图是拉新入口。如果图上直接写出代价，收到图的人就已经知道结果，点进链接的动机消失；而玩家自己也不愿意把「代价」当成海报发出去。 |
| 决定 | `share.js` 的 `createShareCard` 只读取名字、头像色、三个品质名和一句钩子（`config.copy.share.hook`）。代码路径完全不访问 `costLabel`、`backScene`、`comboText`、弱维句。图上保留「矛盾体」小标记，因为它本身就是悬念，不泄露代价。 |
| 放弃了什么 | 放弃了「信息完整」的分享图：收到图的人看不到代价，也看不到组合文案。换来的是明确的点击理由——想知道这三个词背后要付什么。代价是分享图和结果页必须保持视觉同源，否则玩家会觉得被误导。 |
| 日期 | 2026-11-07 |

## 7. 零依赖、无构建，数据与逻辑分离

| 栏 | 内容 |
|---|---|
| 背景 | 这个项目要能直接丢给朋友玩，也要能被当作教学样本逐行阅读。任何构建链、包管理或 CDN 都会同时破坏这两件事：朋友打不开，学习者先被环境劝退。 |
| 决定 | 原生 HTML + CSS + JavaScript（ES module），不引任何第三方库、字体文件、图片文件。文件按职责拆开：`index.html` 只放结构，`styles.css` 只放样式，`game.js` 只放流程与状态，`data/traits.js`、`data/combos.js`、`data/config.js` 放全部数据与文案。分享卡新增 `share.js`（绘制）与 `qr.js`（自写二维码编码器），界面文案一律读 `config.copy`。 |
| 放弃了什么 | 放弃了框架带来的开发效率与组件复用，也放弃了用现成二维码库省事的选项（改为自己实现 byte 模式、版本 1–3、纠错 M 的编码器，并用 OpenCV 实测解码）。代价是所有能力都要手写，且 `game.js` 会偏长（约 780 行）。 |
| 日期 | 2026-11-07 |

## 8. 部署走 GitHub Pages；推送失败时改用 API 通道

| 栏 | 内容 |
|---|---|
| 背景 | 需要给朋友一个公开链接，而不是让他们装本地服务。本机没有 Homebrew、没有 `gh`、没有现成 token；`github.com` 的 HTTPS 连接还持续抖动，`git push` 多次出现速度过慢与端口超时。 |
| 决定 | 部署到 GitHub Pages（public 仓库 `tarot-card`，`main` 分支、根目录）。所有资源保持相对路径，以适配 `/tarot-card/` 子路径。`gh` 用官方 arm64 发布包装到 `~/.local/bin`；当 `git push` 连续失败时，改用 `api.github.com` 的 Git Data 接口（blob → tree → commit → 更新 ref）写入同一份内容，再轮询 Pages 构建到 `built` 并在公网实际打开验证。 |
| 放弃了什么 | 放弃了「只走标准 git 流程」的纯粹性：远端会出现一个由 API 创建、与本地内容相同但 SHA 不同的提交（本地 `a10427c` / 远端 `696f2d4`）。也放弃了「换网络环境再推」这种更省事但不可控的做法。代价是下次本地开发前需要先同步远端，否则历史会分叉。 |
| 日期 | 2026-11-07 |

## 9. 卡池从 12 张扩展到 16 张

| 栏 | 内容 |
|---|---|
| 背景 | 原 12 张卡在「吵完怎么收场」「生活细节」「钱怎么花」「身体亲密怎么开口」这四块语义上是空的；玩家能配出的关系样本不够用。同时现有负值过度集中在「空间」和「稳定」，导致三张卡几乎必然在这两维吃亏。 |
| 决定 | 新增 4 张：`repair` 大度、`order` 干净、`money` 节俭、`direct` 主动；卡池变为 16 张，`config.cardNumerals` 补齐到 `XVI`。新卡的四维负值优先落在「安全感」和「强度」：大度 `security -1 / intensity -2`、干净 `intensity -2`、节俭 `intensity -3`、主动 `security -2`，不再往空间与稳定堆负值。四张卡仍遵守「同一场景两种走法」与短 `costLabel`。 |
| 放弃了什么 | 放弃了「12 张刚好铺满 3 列 × 4 行」的规整，也放弃让每张新卡都显得讨喜。代价是移动端选卡页变长（2 列 × 8 行），桌面端末行只有 4 张；同时新卡的负值会改变部分三张组合的弱维与总分。 |
| 日期 | 2026-11-07 |

## 10. 数据三分离：品质卡 / 场景 / 组合靠 id 关联

| 栏 | 内容 |
|---|---|
| 背景 | 原先把 `frontScene`、`costLabel`、`backScene` 和 `axes` 都塞在同一张卡里，改一句场景文案就要动卡数据；组合也混在同一份数据的心智模型里，新增内容容易误伤。 |
| 决定 | 拆成三份互不依赖的数据文件：`data/traits.js` 只放 `id` / `name` / `sceneId` / `axes` / `relations`；`data/scenes.js` 以场景 id 为 key 存 `frontScene` / `costLabel` / `backScene`；`data/combos.js` 继续只放组合。卡片通过 `sceneId` 指向场景，组合通过 `traits` 里的品质 id 指向卡；`game.js` 的 `sceneOf(id)` 是唯一的运行时关联点。改场景只动 `scenes.js`，改组合只动 `combos.js`，都不需要碰 `traits.js`。 |
| 放弃了什么 | 放弃了「一张卡的所有信息都在同一个对象里」的直观性：现在读一张卡要跨两个文件。也放弃了在卡数据里直接写文案的便捷。代价是新增卡必须同时维护 `traits.js` 与 `scenes.js` 两条记录，且两边 id 必须一致；运行时不校验缺失，靠 `sceneOf` 的兜底不报错但不显示文案。 |
| 日期 | 2026-11-07 |

## 11. 四维得分：线性映射到 20～25，四维相加为 80～100（2026-11-08 由第 12 条改为按实际分布标定）

| 栏 | 内容 |
|---|---|
| 背景 | 四维原先只用来算「弱维台词」，玩家看不到量化结果；如果直接展示原始 -9～9 的负数，既难读也容易把「低分」误解成「坏」。 |
| 决定 | 每张卡每维仍取 -3～3；三张卡按维求和落在 -9～9，按 `20 + round((sum + 9) / 18 × 5)` 四舍五入映射为 20～25，四维相加即总分 80～100。原边界写在 `config.axisRange` 与 `config.scoring.minPerAxis / maxPerAxis`，原计算在 `game.js` 的 `scoreOf` / `computeResult`；2026-11-08 这套逐维映射已由第 12 条替换，但结果页展示总分与四维、分享图只画总分的边界不变。 |
| 放弃了什么 | 放弃了从 0 分起算的宽区间，也放弃了给总分做加权（四维等权）。代价是四维都在 20～25，实际总分集中在 90～95，区分度更窄；分数只作为同池内的相对参考，不设排行榜或阈值。旧卡没有 `scores` 字段时不补算、不显示，避免用新规则改写玩家已有的卡。 |
| 日期 | 2026-11-08 |

## 12. 分数按实际分布标定：原始总分 51～71 拉开到 80～100

| 栏 | 内容 |
|---|---|
| 背景 | 第 11 条的逐维映射把 -9～9 硬铺到 20～25，但 16 张卡的实际数值让 560 种三卡组合的原始总分（单维 0～25 求和）只落在 51～71；映射后总分全挤在 90～95，区分度几乎为零。 |
| 决定 | 先把单维原始和 -9～9 线性映射成 0～25 的「原始分」，四维相加得到原始总分；再按实测锚点 51→80、71→100 线性拉开并钳制在 80～100。锚点写在 `config.scoring` 的 `rawTotalFloor` / `rawTotalCeiling` / `minTotal` / `maxTotal`，注释说明它们来自当前 16 张卡的实际分布；计算在 `game.js` 的 `rawScoreOf` / `totalScoreOf`。四维分项以 20 为底，把总分超出 80 的部分按各维原始分占比分摊，最大余数法保证四项之和严格等于总分（`splitTotal`）。 |
| 放弃了什么 | 放弃了每维独立映射与固定 20～25 的分项区间：独立映射会让分项之和与总分差 1～4 分。代价是锚点与卡牌数值强耦合，改 `axes` 后必须重跑 560 种组合并同步 51/71 两个锚点，否则分布会重新偏斜；分项实际落在 20～27，不再等宽。 |
| 日期 | 2026-11-08 |

## 13. 组合命中后随机取一条，数组顺序不再决定结果

| 栏 | 内容 |
|---|---|
| 背景 | 三张牌能凑出三对，原先只要命中就用 `combos` 数组的第一条。新增组合只能排在旧组合后面，数组顺序实际变成了隐式优先级；玩家也永远看不到同样命中的其他文案。 |
| 决定 | 先筛出所有命中的组合（`pickCombo`），再用 `randomIndex` 随机取一条；随机入口只集中在 `game.js` 的 `randomIndex` 一个函数里，以后要固定种子只改它。`data/combos.js` 的排列只为分组阅读，文件头注释已写明顺序不影响结果。兜底模板保持原样。 |
| 放弃了什么 | 放弃了「同一组三张牌永远得到同一条文案」的确定性：同一选择重复建卡可能得到不同组合文本。换来的是每条命中的组合都能被看到。代价是测试具体文案必须固定 `Math.random`，已有存档卡不会被改写。 |
| 日期 | 2026-11-08 |
